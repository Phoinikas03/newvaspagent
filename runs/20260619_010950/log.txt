27→\n    28→准备启动 VASP（无论经 `vasp_runner.py` 还是 Slurm/PBS 脚本内的命令）时，须遵循下列映射，**严禁**在未对齐硬件的前提下凭习惯使用过大 `-np`（例如不经询问默认 `-np 16` / `-np 64`）。\n    29→\n    30→- **GPU 加速（OpenACC 等 GPU 构建）**\n    31→  - **缺省心智模型（务必牢记）**：在典型 GPU 环境下，**一块物理 GPU 对应一个（并发）VASP 任务**；每个任务独占一组可见设备，且 **`mpirun` 对该任务使用 `-n 1` 或 `-np 1`**，与「一卡一进程」对齐。**手写启动范式**：`CUDA_VISIBLE_DEVICES=i mpirun -n 1 <gpu_exe>`（或 `mpirun -np 1`；`i` 为设备索引，`0`、`1`、…）。多任务并发时依次为不同 `i` 各起一条上述命令（或由 `vasp_runner.py --gpu-per-task 1` 等价生成），**禁止**在单任务内对单卡使用 `-np`>1 除非用户明确要求多卡并行同一计算。\n    32→  - **映射规则**：通常 **1 个 MPI rank ↔ 1 块物理 GPU**（与 `vasp_runner.py` 的 `--gpu-per-task` 为各任务设置 `CUDA_VISIBLE_DEVICES` 一致；细节见 `references/orchestration.md` §3）。\n    33→  - **可执行文件名**：不少站点提供独立名 **`vasp_gpu`**；也有许多环境把 **GPU 版仍叫做 `vasp_std`**，或通过路径/模块区分（例如安装布局里的 **`vasp_std/gpu`**、`bin/gpu/vasp_std` 等）。**以用户模块与 `command -v` 为准**；`vasp_runner.py` 的 `--exe` 应填**实际会出现在 `mpirun … <exe>` 中的名字或 PATH 可解析名**。\n    34→  - **单任务单卡**：只跑一个任务且占用 1 卡 → **`mpirun -np 1`**，`<exe>` 为上述 **GPU 构建**入口；`np` 必须与该任务实际占用的 GPU 数一致。\n    35→  - **单任务多卡**：同一计算使用多块 GPU（例如 4 卡）→ **`mpirun -np 4`**（或与用户/站点约定的 GPU 绑定方式一致），`<exe>` 仍为 GPU 构建入口。\n    36→  - **多任务并发**：多个独立任务并行时，每任务宜 **每卡 `np=1`**，并用 **互斥的 `CUDA_VISIBLE_DEVICES`** 隔离（或由 `vasp_runner.py --gpu-per-task 1` 自动生成）。例如任务 A：`CUDA_VISIBLE_DEVICES=0 mpirun -np 1 <gpu_exe>`；任务 B：`CUDA_VISIBLE_DEVICES=1 mpirun -np 1 <gpu_exe>`（`<gpu_exe>` 可为 `vasp_gpu` 或站点上的 `vasp_std` 等）。禁止多任务无约束地争用同一 GPU。\n    37→- **纯 CPU（CPU-only 构建）**\n    38→  - 使用 **仅 CPU** 的 VASP 可执行文件时，为本任务预留的 **`-np`** 可与为该任务分配的 **物理核心数** 一致（或按站点策略略小于核心数以防过载）；仍须在 Step 2–3 中与用户确认，禁止默认定大核数。**勿**把「名为 `vasp_std`」自动当成纯 CPU——若该二进制实为 GPU 构建，仍按上文 GPU 映射与 `--gpu-per-task` 处理。\n    39→\n    40→**可执行名与工具链**：`probe_env.py` 中的 `vasp_std_found` / `vasp_gpu_found` 只反映默认名是否在默认 PATH 下命中；**最终合法性以 `source env_script` 后** `vasp_runner.py` / `verify_local_dependencies` 能否找到 **`--exe` 所指可执行文件**为准。向用户确认命令时，应写出**真实**的 `<exe>`（无论是 `vasp_gpu` 还是 GPU 版 `vasp_std`）。\n    41→\n    42→### 2. 强制命令确认审查 (Exact Command Confirmation)\n    43→\n    44→在调用 `Bash` 或 `TaskOutput` **真正启动**计算前，**必须**停下并向用户展示：（1）Step 2 得到的**硬件与调度摘要**（CPU/GPU GPU。当前收敛测试第一步采用单卡单任务。拟执行：`source ./template/env_local.sh && python .claude/skills/run_vasp/scripts/vasp_runner.py --dirs <dir> --mode local --np 1 --exe vasp_gpu --gpu-per-task 1 --env-script ./template/env_local.sh --log-file vasp_pbe.log`（若站点 GPU 入口为 `vasp_std`，则将 `--exe vasp_std`）。是否同意？」\n    47→\n    48→**与迭代工作流的关系**：命令确认针对**当前拟执行的这一步或这一批**；若上游 skill 要求逐点/逐目录核查，仍须遵守下文 Step 4 的 Ownership & Safe Termination)\n    51→\n    52→- **默认禁止全局杀进程**：严禁使用 `pkill`、`killall`、`pkill -f vasp_std`、`killall vasp_std`、`kill $(pgrep ...)` 之类按名字/模式批量终止 VASP 或 MPI 进程的命令。\n    53→- **强制使用终止入口**：用户要求停止/暂停/取消某个 VASP 任务时，不得临场手写 shell kill 管道。优先使用：\n    54→  - 有状态文件：`cd "<repo_root>" && python .claude/skills/run_vasp/scripts/terminate.py --work-dir "<task_dir>" --reason "<reason>"`\n    55→  - 旧的手写启动任务、没有 `.vasp_run_state.json`：先运行 `cd "<repo_root>" && python .claude/skills/run_vasp/scripts/terminate.py --work-dir "<task_dir>" --allow-cwd-scan --dry-run` 展示候选 PID；只有当输出中的每个 PID 都明确显示 `/proc/<pid>/cwd` 精确等于目标目录时，才允许去掉 `--dry-run` 执行终止。\n    56→- **特别禁止 `pkill -f`**：它会匹配执行该命令的 shell/工具包装进程自身命令行，可能把消息读取器或 agent 进程一并杀掉，出现 `exit code -15` / `Fatal error in message reader`。\n    57→- **只能处理自己启动的任务**：若需要停止任务，你必须先证明该 PID 或作业 ID 是你在当前工作流中亲自启动的那一个，证据应来自：\n    58→  - 你刚刚启动时记录的 `task_id`、作业 ID、日志路径或目录；\n    59→  - `ps` / `squeue` / `qstat` / 任务输出能明确对应到当前工作区或当前这批目录；\n    60→  - 日志或文件时间戳表明该进程确实属于当前 run，而不是系统中其它人的/其它目录的 VASP。\n    61→- **仅凭名字不算证据**：`pgrep -f vasp_std`、`ps | grep vasp_std`、进程数量统计，最多只能说明“系统里有 VASP 在跑”，**不能**说明这些进程属于当前任务，因此**绝不能**据此执行终止。\n    62→- **先核实，再决定是否停**：在考虑终止前，先检查是否真的需要停止，例如：\n    63→  - 关联目录的日志是否持续增长；\n    64→  - `OUTCAR` / `vasp_run_*.log` 是否仍有新内容；\n    65→  - 对应 `task_id` / 作业状态是否已经结束但残留了子进程；\n    66→  - 用户是否明确要求“停止”而不是“继续等待”。\n    67→- **必须定点终止**：只有在完成上述核实且确需停止时，才允许对**已确认属于当前任务**的具体 PID 或作业 ID 进行定点终止；优先使用最窄范围的命令。\n    68→- **无法证明所有权时的正确行为**：停止自动处置，向用户汇报“发现有同名进程，但无法证明属于当前任务”，并请求确认；不得擅自清场后重提。\n    69→\n    70→### 4. 同目录重启与 GPU 报错恢复 (In-place Retry & GPU Failure Recovery)\n    71→\n    72→- **禁止同目录双开**：若某个工作目录（如 `pbe_scf`、`hse_scf`、某个 `e_400` / `k_0.15` 目录）里的 VASP 因 GPU/MPI 报错需要重试，**不得**在旧进程可能仍存活时，再向同一目录启动第二个 `mpirun` / `vasp_*`。尤其禁止直接写 `... mpirun ... > same.log 2>&1 &` 作为“补救重跑”。\n    73→- **先证据、后重启**：重启前必须拿到旧运行的所有权证据，例如你刚启动时的 `task_id`、`vasp_runner.py` 命令、`ps` 中带工作目录的命令行、对应日志路径。然后确认旧运行是否还活着。\n    74→- **若旧运行仍在**：只能定点终止该旧运行的精确 PID / 作业 ID / 该任务产生的进程树；等待它们实际消失后，才允许继续重启。不得只凭“应该失败了”或看到报错片段就直接补开新进程。\n    75→- **优先继续使用 runner**：即使只是换 GPU 布局（例如从 8 卡改成 7 卡，避开坏卡），也应优先重新调用 `python .claude/skills/run_vasp/scripts/vasp_runner.py ...` 或 `quick_test.py`，而不是手写新的正式 `mpirun` 提交。\n    76→- **同目录重跑时的日志规则**：只有在旧运行已确认结束或已被定点终止后，才允许继续写同一个日志文件；否则应先停旧运行。不要让两个活跃 VASP 进程同时写同一目录或同一 `vasp_*.log`。\n    77→- **对用户的说明**：发生 GPU 报错后的恢复方案必须向用户明确说明：旧运行是否仍在、是否已定点清理、替代的 GPU 布局是什么、重启命令是什么。\n    78→\n    79→---\n    80→\n    81→## 工作流 (Workflow)\n    82→\n    83→### Step 1: 意图识别 (Intent Recognition)\n    84→- 询问用户或分析
